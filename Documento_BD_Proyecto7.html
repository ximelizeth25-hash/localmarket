1 Descripción y Justificación del Gestor de Base de Datos

Para la implementación y persistencia del sistema LocalMarket (Proyecto 7), se ha seleccionado PostgreSQL como Sistema Gestor de Base de Datos Relacional Orientado a Objetos (ORDBMS). PostgreSQL es ampliamente reconocido en la industria por su robustez, estricto cumplimiento de estándares SQL, integridad referencial avanzada y capacidad de soportar cargas transaccionales complejas de comercio electrónico.

Ficha Técnica del SGBD:
Motor: PostgreSQL versión 15 / 16 | Dialecto: PL/pgSQL | Base de Datos: proyecto7 | Puerto por defecto: 5432

Justificación de la Elección de PostgreSQL

1. Cumplimiento Estricto de Propiedades ACID

Garantiza Atomicidad, Consistencia, Aislamiento y Durabilidad en todas las operaciones críticas. Al procesar una compra directa, la generación del pedido, la inserción del detalle y la reducción del inventario se ejecutan en una sola transacción sin inconsistencias.

2. Control de Concurrencia Multiversión (MVCC)

Permite que múltiples clientes consulten el catálogo de productos y lean métricas concurrentemente sin bloquear las escrituras o actualizaciones de inventario efectuadas por los vendedores.

3. Programabilidad Avanzada (PL/pgSQL)

Soporte nativo para Triggers (disparadores para evitar stock negativo), Funciones Almacenadas (validación de disponibilidad) y Vistas optimizadas para reportes gerenciales.

4. Integridad Referencial y Tipado Fuerte

Validaciones estrictas de claves foráneas con reglas de eliminación/actualización en cascada o restricción, tipos de datos precisos para valores monetarios (numeric(12,2)) y timestamps sin desfase.

2 Descripción y Justificación del Lenguaje de Programación

El ecosistema de desarrollo de LocalMarket está construido sobre una arquitectura Full-Stack JavaScript, utilizando Node.js en el servidor y JavaScript Moderno (ES6+) en el cliente, comunicados mediante una API RESTful en formato JSON.

Arquitectura Tecnológica del Stack:

  • Entorno de Ejecución Backend: Node.js (V8 Engine) - E/S Asíncrona no bloqueante basada en eventos.
  • Framework Web HTTP: Express.js - Enrutamiento modular por dominios de negocio (routes/).
  • Controlador de Conexión a BD: Driver pg (node-postgres) con Connection Pooling parametrizado para evitar inyecciones SQL.
  • Frontend & UI: HTML5 Semántico, Tailwind CSS (diseño responsivo de alto rendimiento), Vanilla JS reactivo.

Ventajas de la Integración Node.js + PostgreSQL

  • Unificación de Lenguaje: Permite compartir esquemas de validación (expresiones regulares de correo electrónico, validación de 10 dígitos telefónicos) entre frontend y backend sin duplicidad.
  • Pool de Conexiones Optimizado: La clase Pool de pg administra eficientemente las conexiones abiertas hacia PostgreSQL, reutilizándolas y evitando el costo de inicialización por cada petición.
  • Consultas Parametrizadas: Todas las consultas SQL implementan sintaxis con marcadores de posición ($1, $2, $3), mitigando al 100% ataques de inyección SQL.

3 Diagrama Entidad-Relación (ERD) General

El esquema relacional de LocalMarket está compuesto por 13 entidades normalizadas en Tercera Forma Normal (3FN), garantizando la no redundancia de datos y una relación lógica coherente entre los módulos de Autenticación, Catálogo, Transacciones, Seguridad y Moderación.

5 Objetos Avanzados de Base de Datos (PL/pgSQL)

Para garantizar la máxima eficiencia en la capa de datos y evitar cálculos repetitivos en el servidor Node.js, se han programado directamente en el motor PostgreSQL las siguientes Vistas, Funciones, Procedimientos Almacenados y Triggers:

1. Vistas Optimizadas (Views)

-- Vista para Catálogo y Búsqueda con nombres legibles
CREATE OR REPLACE VIEW vw_productos_detallados AS
SELECT p.id_producto, p.titulo, p.descripcion, p.precio, p.costo_unitario, p.stock, 
       p.imagen_1, p.imagen_2, p.imagen_3,
       COALESCE(c.nombre, 'Sin categoría') AS categoria_nombre, 
       COALESCE(u.nombre, 'Vendedor Principal') AS vendedor_nombre
FROM PRODUCTOS p
LEFT JOIN CATEGORIAS c ON p.id_categoria = c.id_categoria
LEFT JOIN USUARIOS u ON p.id_vendedor = u.id_usuario;

-- Vista de Alerta de Stock Bajo (Nivel de Reorden <= 5)
CREATE OR REPLACE VIEW vw_productos_stock_bajo AS 
SELECT p.id_producto, p.titulo, p.id_categoria, p.stock, 
       COALESCE(c.nombre, 'General') AS categoria_nombre
FROM PRODUCTOS p
LEFT JOIN CATEGORIAS c ON p.id_categoria = c.id_categoria
WHERE p.stock <= 5;

2. Funciones y Procedimientos Almacenados (Stored Procedures)

-- Función: Validar existencia suficiente antes de compra
CREATE OR REPLACE FUNCTION fn_validar_stock_disponible(p_id_producto INT, p_cantidad INT)
RETURNS BOOLEAN AS $$
DECLARE
    v_stock INT;
BEGIN
    SELECT stock INTO v_stock FROM PRODUCTOS WHERE id_producto = p_id_producto;
    RETURN (v_stock >= p_cantidad);
END;
$$ LANGUAGE plpgsql;

-- Procedimiento: Procesar venta atómica y descontar inventario
CREATE OR REPLACE PROCEDURE sp_procesar_venta(
    p_id_pedido INT, p_id_producto INT, p_cantidad INT, p_precio_unitario NUMERIC
)
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO DETALLE_VENTA (id_pedido, id_producto, cantidad, precio_unitario, subtotal_item)
    VALUES (p_id_pedido, p_id_producto, p_cantidad, p_precio_unitario, (p_cantidad * p_precio_unitario));
    
    UPDATE PRODUCTOS SET stock = stock - p_cantidad WHERE id_producto = p_id_producto;
END;
$$;

3. Triggers de Integridad (Disparadores)

-- Trigger para evitar inventarios negativos
CREATE OR REPLACE FUNCTION trg_fn_auditar_producto()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.stock < 0 THEN
        RAISE EXCEPTION 'Error de Integridad: El stock del producto no puede ser negativo.';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_auditoria_productos
BEFORE UPDATE ON PRODUCTOS
FOR EACH ROW EXECUTE FUNCTION trg_fn_auditar_producto();

7 Conclusiones y Consideraciones de Operación

El diseño e implementación de la base de datos para LocalMarket (Proyecto 7) cumple rigurosamente con los más altos estándares de la ingeniería de software:

  • Seguridad y Resiliencia: Esquema blindado contra inyecciones SQL mediante consultas preparadas en el driver pg, con autenticación en dos factores (OTP) y moderación de cuentas.
  • Escalabilidad: La separación clara entre cabeceras de ventas (PEDIDOS_VENTAS) e ítems (DETALLE_VENTA) permite registrar miles de transacciones diarias sin degradación de velocidad.
  • Consistencia y Automatización: Los disparadores y vistas garantizan que la información consultada por la capa de presentación refleje en tiempo real el inventario físico disponible.
